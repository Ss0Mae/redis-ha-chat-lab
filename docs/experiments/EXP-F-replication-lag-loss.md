# EXP-F. 복제 지연 상태의 Primary 종료 — 승인된 쓰기는 얼마나 사라지는가

```text
실험 이름: faults/NETEM_REPLICATION_DELAY_THEN_KILL_PRIMARY (Sentinel, Cluster 각 5회) + settings/* (설정 변형, EXP-SETTINGS 에 별도 정리)
검증하려는 가설: 복제가 비동기이므로 Primary 가 ACK 한 뒤 Replica 에 못 간 쓰기는 승격 후 사라진다. 유실 건수는 지연 × 쓰기율에 비례한다.
변경한 항목: Primary 사이드카에서 tc netem 으로 Replica IP 로 나가는 패킷에만 500 ms 지연 → 10 초 동안 쓰기를 쌓아 offset 차이를 만든 뒤 Primary SIGKILL.
통제한 조건·서버 사양·데이터·부하: EXP-A/B 와 같음. 쓰기 비율 45%(SET 20 / INCR 10 / SEND 15) → 초당 약 135 건.
```

5회 값(Sentinel 유실 건수): 24, 25, 23, 34, 25 (평균 26.2, 표준편차 4.4). 계산: 지연 0.5 s × 초당 쓰기 135 건 ≈ 68 건이 "Replica 에 아직 도착하지 않았을" 상한이고, 그중 SET 은 같은 사용자의 뒤 쓰기로 덮이거나, SEND 는 멱등 Lua 로 재시도되며 스트림에 남아 실제 유실은 25 건이었다.

## 병목 원인·해석

- **Sentinel 에서 유실이 0 → 25 로 늘어난 것**이 비동기 복제의 창이다. Primary 는 Replica 의 ACK 를 기다리지 않고 응답하므로, 죽는 순간 전송 중이던 0.5 초 분량이 승격된 Replica 에 없다. 지연이 없을 때 0 인 이유는 같은 VM 안의 복제 지연이 수 ms 라 그 창에 든 쓰기가 SET 의 경우 뒤 쓰기로 덮이고 INCR 은… 0 이었다(5회 모두).
- **Cluster 는 지연 유무와 관계없이 35~38 건**이다. 잘못된 값 키(34)와 유실(38)이 거의 같고 INCR 중복(32)이 함께 나온다는 점에서, 복제 창보다 "재연결 뒤 늦게 실행된 옛 명령"(EXP-A/B 해석 참고)이 지배한다. 그 위에 복제 창 분량이 얹혀야 하는데 차이가 3 건 안팎이라 5회 편차(36~50) 안에 묻힌다.
- 메시지(SEND) 유실이 두 구성 모두 0 인 것은 앱이 실패한 전송을 같은 `clientMsgId` 로 재시도하고 Lua 가 dedupe 키로 멱등 처리하기 때문이다. 즉 **"승인 후 유실" 은 클라이언트가 재시도하지 않는 쓰기(SET presence)에서만 남았다.**

## 부작용

지연 주입은 Primary→Replica 방향에만 걸었으므로 Replica 의 ACK(REPLCONF) 는 지연이 없다. `min-replicas-max-lag` 는 이 ACK 시각으로 lag 를 재기 때문에 500 ms 지연에서는 lag 가 1 s 를 넘지 않아 쓰기를 막지 못한다 — EXP-SETTINGS 의 가설.

## 결론

Sentinel 기본 설정에서 복제 지연 0.5 s 는 승인 쓰기의 0.37%(25건/약 5,400건)를 사라지게 했다. Cluster 도 같은 구조지만 이 실험 조건에서는 늦은 실행이 만든 잘못된 값이 더 커서 지연 효과를 분리해 보려면 `REJECT_COMMANDS` 변형이 필요하다(EXP-OPT).

## 다음 실험
