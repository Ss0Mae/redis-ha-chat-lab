# EXP-MISC. 실험 기록 방식이 측정에 미치는 영향, 앱↔Sentinel 경로 장애(Toxiproxy)

```text
실험 이름: misc/recording-{MEMORY,BATCH,SAMPLED}/NONE/sentinel/rps1000/rep1~3 (9회, 장애 없음),
          misc/TOXIC_APP_SENTINEL_{TIMEOUT,LATENCY}/sentinel-toxi/rps300/rep1~3 (6회)
검증하려는 가설: (1) 요청마다 행을 큐에 넣는 BATCH 는 MEMORY 보다 Redis 명령 p95 와 앱 CPU 가 높고, SAMPLED 는 그 사이다.
                (2) Sentinel 은 프록시가 아니므로, 앱↔Sentinel 경로가 끊기거나 느려져도 이미 연결된 Primary 로의 명령은 영향이 없다.
변경한 항목: (1) 실험 생성 시 recordingMode 만 변경. (2) 앱의 Sentinel 주소를 Toxiproxy(172.28.0.50:26379 → s-1) 로 두는 sentinel-toxi 프로필에서 toxic(timeout / latency 300 ms) 추가.
통제한 조건: (1) Sentinel, 앱 내부 워크로드 1,000 RPS, 사용자 10,000·방 100, 워밍업 15 s → 측정 60 s, 같은 앱 이미지·JVM. 순서는 MEMORY → BATCH → SAMPLED 를 3회 반복.
             (2) 300 RPS, 워밍업 10 → 정상 30 → toxic 40 → 제거 40 s, EXP-A/B 와 같은 조건.
서버 및 DB 사양: EXP-PERF 와 같음(앱 cpus 2.0 / 1 GB, Redis cpus 1.0 / 512 MB, MySQL 8 컨테이너).
테스트 데이터: FLUSHALL 후 시작. (1) 회당 승인 쓰기 약 33,600~34,100건, request_log 행 BATCH 약 60,000 / SAMPLED 약 600 / MEMORY 0, metric_sample 60행.
전체 요청 수·지속시간: (1) 회당 60,000(60 s). (2) 회당 36,000(120 s).
```

## 병목 원인·해석

- **가설 (1) 은 기각됐다 — 방향이 반대였다.** BATCH 의 p95 가 0.49 ms 로 MEMORY(0.76)·SAMPLED(0.86)보다 0.3 ms 낮았고, 앱 CPU 는 세 모드가 0.046~0.051 로 측정 오차 안(회차 간 편차 0.003~0.013)이었다. 요청 스레드가 하는 일은 세 모드에서 같다(장부 기록 + 초 집계 + BATCH/SAMPLED 는 `ArrayBlockingQueue.offer` 한 번, DB 대기 없음). 다른 것은 배경 활동량이다: BATCH 에서는 기록 스레드가 초당 두 번 500행 배치 INSERT 를 하고 MySQL 이 계속 일한다. 이 장비에서는 **활동이 많을수록 지연이 낮아지는** 현상이 EXP-PERF 정상 구간(100 → 2,000 RPS 에서 p50 0.94 → 0.27 ms)에서도 같은 방향으로 나타났으므로, 유휴 코어·스레드를 깨우는 비용(CPU 절전·스케줄링)이 0.3 ms 차이의 원인이라고 추정한다(검증하지 않음). ADR-005 의 목표였던 "기록이 요청 경로를 느리게 하지 않는다" 는 확인됐다: 요청마다 행을 남기는 BATCH 를 정합성 실험뿐 아니라 성능 비교에 써도 측정을 망치지 않았을 것이고, 큐 20만 개 중 드롭은 1,000 RPS 에서 0 이었다.
- **가설 (2) 확인.** 앱↔Sentinel 경로를 40 s 동안 끊거나(timeout toxic) 300 ms 지연시켜도 오류 0, p95 변화 0, 유실 0 이었다. 앱은 기동 때 Sentinel 에서 Primary 주소를 얻어 **Redis 에 직접 연결**하고 그 뒤로는 재연결이 필요할 때만 Sentinel 에 다시 묻는다(Spring Boot 기본 연결은 `+switch-master` 구독도 하지 않는다, EXP-OPT). 따라서 Sentinel 경로 장애는 "Failover 가 필요한 순간" 과 겹칠 때만 문제가 되고, 그때는 EXP-DE 의 Sentinel 전부 중지와 같은 결과(Failover 불가 → 전면 중단)가 된다. Sentinel 3대 전부를 멈춘 EXP-DE 의 `STOP_ALL_SENTINELS`(오류 0 %) 와 함께, "Sentinel 은 데이터 경로에 없다" 를 두 방향에서 확인했다.
- Toxiproxy 를 앱↔Primary 사이에는 둘 수 없었던 이유(Failover 뒤 새 주소로 우회됨, ADR-003)와 대비하면, 이 경로가 프록시 실험이 가능한 유일한 정적 주소다.

## 부작용·한계

- 기록 방식 비교는 1,000 RPS·60 s 3회다. 더 긴 실행에서 request_log 가 수백만 행으로 커지면 INSERT 비용이 달라질 수 있다(이 프로젝트 전체에서 1,470만 행까지는 드롭 0).
- `process_cpu_usage` 는 JVM 프로세스의 CPU 사용률(가용 코어 대비 비율)이라 컨테이너 상한(2.0 코어)이 아닌 VM 코어 수 기준일 수 있다. 세 모드의 상대 비교에만 쓴다.
- LATENCY rep2 실행 중 세 Sentinel 이 같은 순간(03:42:49) `+tilt` 를 냈다. 호스트 절전 기록·앱 초별 표본 공백·컨테이너-호스트 시계 차이가 모두 없어 VM 시계 보정(역행)으로 추정한다. Redis 장애가 없는 실험이라 결과에는 영향이 없고, TILT 는 30 s 뒤 풀려 다음 배치(03:48) 와 겹치지 않았다.

## 결론

기록 방식은 Redis 명령 지연과 앱 CPU 에 측정 가능한 부담을 주지 않았고(오히려 BATCH 가 0.3 ms 빨랐다), 앱↔Sentinel 경로 장애는 데이터 경로에 아무 영향이 없었다. 두 결과 모두 설계의 전제(기록을 요청 경로에서 분리, Sentinel 은 감시자일 뿐)를 실측으로 확인한 것이다.
